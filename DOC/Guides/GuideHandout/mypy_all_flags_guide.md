# Полный гид по флагам MyPy: От типов к бизнес-логике

Этот документ содержит описание ключевых флагов MyPy, их участие в режиме `--strict` и, главное, их влияние на стабильность и логику приложения с точки зрения QA.

---

## 1. Группа "Strict Mode" (Автоматически включаются флагом `--strict`)
*Это базовый набор для обеспечения TYPE SAFETY. Если эти флаги выключены, MyPy начинает "прощать" ошибки, которые могут привести к багам.*

| Флаг | Входит в `--strict` | Техническое значение | Бизнес-риск / Что проверяет QA |
| :--- | :---: | :--- | :--- |
| `warn_unused_configs` | ✅ Да | Ругается, если в конфиге есть настройки для несуществующих файлов. | **Риск дезинформации.** Мы можем думать, что модуль проверяется строго, а на самом деле из-за опечатки в конфиге он не проверяется вовсе. |
| `disallow_any_generics` | ✅ Да | Запрещает использовать `list` или `dict` без указания типов содержимого. | **Риск падения циклов.** Если мы ждем `list[str]`, а пришел `list[int]`, приложение упадет при первой же попытке обработать строку. |
| `disallow_subclassing_any` | ✅ Да | Запрещает наследоваться от классов с типом `Any`. | **Риск хрупкой архитектуры.** Если базовый класс — "черный ящик", мы можем случайно сломать всю иерархию объектов в приложении. |
| `disallow_untyped_calls` | ✅ Да | Запрещает вызывать типизированные функции из нетипизированного кода. | **Риск "отравления" данных.** Не дает непроверенным данным попасть в надежные части системы. |
| `disallow_untyped_defs` | ✅ Да | Требует аннотации типов для всех функций. | **Защита от "слепых зон".** Гарантирует, что разработчик не "спрячет" плохую логику в функции без типов. |
| `disallow_incomplete_defs` | ✅ Да | Запрещает частичные аннотации (например, только входные данные без выхода). | **Риск неопределенности.** Мы можем подать верные данные, но получить "что-то", что взорвет логику дальше. |
| `check_untyped_defs` | ✅ Да | Проверяет тела функций без аннотаций. | **Поиск опечаток.** Позволяет найти технические ошибки даже там, где типы еще не проставлены. |
| `disallow_untyped_decorators` | ✅ Да | Запрещает использовать декораторы, у которых нет типов. | **Риск искажения логики.** Декораторы часто меняют поведение функций (например, логика доступа или кэширования). Если декоратор без типа — MyPy не видит, что он делает. |
| `no_implicit_optional` | ✅ Да | Запрещает `arg: str = None`. Нужно явно `Optional[str]`. | **Защита от забытого сценария.** Заставляет разработчика явно продумать: "А что, если данных нет?". |
| `warn_redundant_casts` | ✅ Да | Находит лишние `cast(type, obj)`. | **Чистота кода.** Помогает понять, что система типов и так справляется, и лишние "подпорки" не нужны. |
| `warn_unused_ignores` | ✅ Да | Ругается на `# type: ignore`, если ошибки в строке больше нет. | **Риск скрытых багов.** Если костыль (ignore) больше не нужен, его надо убрать, иначе он может скрыть новую, реальную ошибку. |
| `warn_return_any` | ✅ Да | Ошибка, если функция возвращает `Any` там, где заявлен конкретный тип. | **Потеря контроля.** Запрещает "дыры" в системе типов на выходе из функций. |
| `no_implicit_reexport` | ✅ Да | Запрещает неявный импорт имен из модулей. | **Риск поломки при обновлении.** Гарантирует, что мы используем только те части кода, которые разработчик модуля разрешил использовать. |
| `strict_equality` | ✅ Да | Запрещает сравнение несовместимых типов (например, `id: int == "1"`). | **Защита "мертвой логики".** Находит условия, которые всегда выдают False, блокируя работу фичи. |

## 2. Группа "Logic & Reliability" (Не всегда в strict, но критичны для QA)
*Эти флаги ищут ошибки в самом ходе мыслей разработчика.*

| Флаг | Рекомендуется | Техническое значение | Бизнес-риск / Что проверяет QA |
| :--- | :---: | :--- | :--- |
| `strict_optional` | **MUST HAVE** | Не дает работать с `Optional` значениями без проверки на `is not None`. | **Главная защита от "500 Error".** Предотвращает падения при пустых данных из API или БД. |
| `warn_unreachable` | **QA CHOICE** | Находит код, до которого нельзя дойти. | **Логический аудит.** Если код недостижим — значит, условия выше написаны неверно, и фича не работает. |
| `warn_no_return` | **ДА** | Ругается, если в функции пропущен `return`. | **Защита от потери данных.** Гарантирует, что функция всегда отдает результат, а не "пустоту" по забывчивости. |
| `allow_redefinition` | НЕТ | Разрешает одной переменной менять тип (сначала int, потом str). | **Риск путаницы.** QA будет сложно понять, в какой момент данные превратились из "цены" в "название". Рекомендуется выключать. |

---

## 3. Группа "Any Control" (Для самых суровых проектов)
*Позволяют полностью искоренить динамическую типизацию.*

| Флаг | Техническое значение | Когда включать? |
| :--- | :--- | :--- |
| `disallow_any_explicit` | Запрещает писать слово `Any`. | Когда проект должен быть типизирован на 100% (банки, медицина). |
| `disallow_any_expr` | Запрещает выражения, которые MyPy не смог вычислить (вывел их как `Any`). | Для борьбы с "невидимыми" пропусками проверок. |
| `disallow_any_decorated` | Запрещает функции, которые после декоратора стали `Any`. | Чтобы декораторы (например, логирование) не ломали типы. |

---

## 4. Группа "Imports & External World"
*Как мы работаем с чужим кодом.*

| Флаг | Значение по умолчанию | Влияние на QA |
| :--- | :--- | :--- |
| `ignore_missing_imports` | Часто `True` | Если `True`, MyPy игнорирует библиотеки без типов. **Риск:** Мы можем неправильно вызывать методы стороннего API (например, Telegram или Stripe) и узнать об этом только в рантайме. |
| `follow_imports` | `normal` | Определяет, как глубоко MyPy зарывается в импорты. Влияет на скорость проверки и глубину обнаружения багов. |

---

### Итоговый совет для QA:
Если ты хочешь быстро оценить "здоровье" проекта, загляни в конфиг и проверь наличие трех китов:
1. `strict = True`
2. `strict_optional = True`
3. `warn_unreachable = True`

Если они есть — разработчики серьезно относятся к качеству. Если нет — готовься к приключениям с `NoneType` и сломанной логикой `if/else`.
