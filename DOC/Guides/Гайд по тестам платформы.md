

### Backend pytest

- **Конфиг**: `backend/pyproject.toml` → `testpaths = "tests"`, `asyncio_mode = "auto"`.
- **Порог покрытия**: `cov-fail-under = 95`.
- **Изоляция БД**: `FakeAsyncPGPool` оборачивает реальное соединение в транзакцию и откатывает её после каждого теста.
- **Фикстуры**: `app`, `initialized_app`, `client`, `authorized_client`, `test_user`, `test_article`, `token`.
- **`APP_ENV=test`**: задаётся в `[tool.pytest.ini_options].env`.

### Покрытые маршруты в pytest

`test_authentication`, `test_login`, `test_registration`, `test_users`, `test_articles`, `test_comments`, `test_profiles`, `test_tags`, `test_error`, `test_422_error`.

### Postman / Newman тесты (`backend/postman/`)

**Файлы:**

| Файл | Назначение |
|------|-----------|
| `Conduit.postman_collection.json` | Коллекция запросов Postman (формат v2.1) |
| `run-api-tests.sh` | Скрипт запуска коллекции через Newman |

**Назначение тестов.** Коллекция реализует полный **функциональный сценарий жизненного цикла** пользователя в системе — от регистрации до удаления данных. Это чёрноящичные API-тесты, которые работают с реальным HTTP-стеком и проверяют корректность контрактов ответов.

**Группы и запросы:**

| Группа | Запросы | Что проверяется |
|--------|---------|----------------|
| **Auth** | Register, Login, Login and Remember Token, Current User, Update User | Структура ответа `user` (email, username, bio, image, token); сохранение JWT в глобальную переменную `token` |
| **Articles** (read-only) | All Articles, Articles by Author, Articles Favorited by Username, Articles by Tag | HTTP 200, структура `articles[]` + `articlesCount`; наличие полей title, slug, body, createdAt, updatedAt (ISO 8601), description, tagList, author, favorited, favoritesCount |
| **Articles, Favorite, Comments** | Create Article, Feed, All Articles (анон + авториз.), Articles by Author, Favorited, Single Article by slug, Articles by Tag, Update Article, Favorite/Unfavorite Article, Create/Get/Delete Comment, Delete Article | Сквозной CRUD; `favorited=true/false`; `favoritesCount > 0`; сохранение `slug` и `commentId` в глобальные переменные |
| **Profiles** | Register Celeb, Profile, Follow Profile, Unfollow Profile | Структура `profile` (username, bio, image, following); `following=true` после подписки, `following=false` после отписки |
| **Tags** | All Tags | HTTP 200, `tags` — массив |

**Глобальные переменные Newman:**

| Переменная | Источник | Использование |
|-----------|---------|--------------|
| `APIURL` | env / дефолт `https://conduit.productionready.io/api` | Базовый URL всех запросов |
| `USERNAME` | env / `u<timestamp>` | Уникальный логин для запуска |
| `EMAIL` | env / `<USERNAME>@mail.com` | Email регистрируемого пользователя |
| `PASSWORD` | env / `password` | Пароль |
| `token` | Сохраняется из ответа Login and Remember Token | Заголовок `Authorization: Token {{token}}` |
| `slug` | Сохраняется из Create Article | URL статьи в последующих запросах |
| `commentId` | Сохраняется из Create Comment | Удаление конкретного комментария |

**Когда полезно запускать:**
- После деплоя — быстрая проверка, что все эндпоинты живы и возвращают корректные структуры.
- При разработке нового фичи — как приёмочный тест перед передачей в CI.
- Для сравнения локальной среды с эталонным API `conduit.productionready.io` — переключить `APIURL`.
- Как альтернатива pytest для тестирования работающего контейнера — не требует Python-окружения, только Node.js.

**Особенность:** тесты внутри групп **Auth** и **Profiles** содержат флаг `if (!(environment.isIntegrationTest))` — при наличии переменной `isIntegrationTest` в Postman-окружении часть ассертов пропускается (для интеграционного запуска без создания новых данных).


# Запуск тестов


### 1. Backend unit/integration тесты (pytest)

**Что тестируется:** маршруты FastAPI, репозитории, JWT-сервис, Pydantic-схемы — без реального HTTP-стека. БД изолирована транзакцией с rollback.  
**Требует:** Python + Poetry. БД `conduit_test_db` должна быть доступна.

#### Запуск локально (без Docker)

```bash
cd backend

# Установка зависимостей (один раз)
poetry install

# Запуск всех тестов с покрытием
poetry run pytest

# Запуск конкретного файла
poetry run pytest tests/test_api/test_routes/test_articles.py

# Без отчёта покрытия (быстрее)
poetry run pytest --no-cov

# Параллельный запуск
poetry run pytest -n auto
```

#### Запуск в Docker (против инфраструктуры)

```bash
docker run --rm \
  --network conduit-network \
  -v "${PWD}/backend:/app" \
  -w /app \
  -e APP_ENV=test \
  -e DATABASE_URL=postgresql://postgres@db:5432/conduit_test_db \
  python:3.9-slim \
  sh -c "pip install poetry && poetry install && poetry run pytest"
```

**Отчёт покрытия** сохраняется в `backend/htmlcov/index.html` и `backend/coverage.xml`.

## 3. `backend/tests` — ядро pytest

### Библиотеки

- **pytest**, **pytest-asyncio** (`asyncio-mode=auto`), **pytest-cov** (порог **95%** по веткам и строкам), **pytest-env**, **pytest-xdist** (параллельный запуск при необходимости).
- **httpx** (`AsyncClient`) — асинхронные HTTP-запросы к приложению **in-process** (без сетевого порта).
- **asgi-lifespan** (`LifespanManager`) — корректный прогон startup/shutdown FastAPI в тестах.

### Конфигурация

- Параметры pytest: `backend/pyproject.toml` → `[tool.pytest.ini_options]` (`testpaths = "tests"`, строгие маркеры, отчёты coverage: terminal, html, xml).
- Доп. настройки coverage: `backend/setup.cfg` (`[coverage:run]`, `[coverage:report]`).

### Паттерны проектирования

1. **Фикстуры pytest** (`conftest.py`): единая точка создания приложения, клиента, пула БД, тестового пользователя, статьи, JWT.
2. **Test double для изоляции транзакций**: `FakeAsyncPGPool` — оборачивает реальный пул **asyncpg**, держит одно соединение и **транзакцию**, в конце делает **rollback**. Все изменения БД в тесте откатываются → **повторяемые** тесты без «грязного» состояния.
3. **Ленивый импорт приложения** в фикстуре `app`, чтобы переменные окружения (`APP_ENV=test`) успели установиться до загрузки настроек.
4. **Arrange–Act–Assert** в тестах маршрутов и сервисов.

### Структура по папкам

| Путь | Назначение |
|------|------------|
| `test_api/test_routes/` | Интеграционные тесты HTTP API: регистрация, логин, пользователи, профили, статьи, комментарии, теги, аутентификация. Проверяются коды ответов, тела JSON, права доступа. |
| `test_api/test_errors/` | Формат ошибок в духе RealWorld (`errors` в теле): **404** и **422** (неверный тип path-параметра). |
| `test_services/test_jwt.py` | Юнит-тесты сервиса JWT: создание токена, извлечение username, ошибки при неверном секрете/форме payload. |
| `test_db/test_queries/test_tables.py` | Юнит-тесты вспомогательного класса `TypedTable` (имя таблицы из атрибута или имени класса). |
| `test_schemas/test_rw_model.py` | Юнит на преобразование datetime в строку API. |

### Какое качество обеспечивают

- **Регрессии** в бизнес-логике и маршрутах.
- **Согласованность** с ожидаемым форматом ошибок клиента.
- Высокое **покрытие кода** (жёсткий порог 95% в CI-настройке pytest).

## 8. `tests/pact` — контрактное тестирование (CDC)

### Роль в архитектуре

- **Потребитель** контракта: «фронтенд» `conduit-frontend` (в тестах — HTTP-клиент к мок-серверу Pact).
- **Провайдер**: `conduit-backend` (FastAPI). Файлы контракта описывают ожидаемые запросы/ответы; провайдер должен их **удовлетворять** при верификации.

### Consumer (`tests/pact/consumer`)

- **Jest** + **@pact-foundation/pact** (Pact V3) + **superagent**.
- Тесты: `*.pact.test.js` — статьи (GET список, POST создание) и аутентификация (login, register).
- **Matchers**: `like`, `eachLike`, `iso8601DateTime` — гибкое сопоставление тел ответов без хрупкого равенства всего JSON.
- Генерация JSON-контрактов в каталог `pacts/` (часто в `.gitignore`).
- `publish-pacts.js` — публикация в **Pact Broker** через **@pact-foundation/pact-node** (`Publisher`).

### Provider (`tests/pact/provider/pact_verifier.py`)

- **pact-python** (`Verifier.verify_with_broker`): забирает контракты с брокера, дергает реальный `PROVIDER_URL`, сравнивает ответы.
- **Provider states**: URL `http://…/api/_pact/provider-states` — бэкенд поднимает данные (пользователи, статьи) под описанные в контракте состояния (`articles exist in the system`, `user is authenticated`, и т.д.). Реализация: `backend/app/api/routes/pact_provider_states.py`.
- Опции: `enable_pending=True`, публикация результатов верификации, ветки/версии через env (`GIT_COMMIT`, `GIT_BRANCH`).

### Паттерны

- **Consumer-driven contracts**: контракт пишется со стороны клиента.
- **Provider states** — явная подготовка данных для каждого сценария (аналог фикстур на уровне интеграции сервисов).

### Методология

- **Contract testing** между независимо деплоимыми частями; брокер — источник истины и история совместимости.

### Какое качество

- Раннее обнаружение **несовместимости API** без полного E2E; защита эволюции API при согласовании через брокер.

### Как запустить вручную

1. Поднять **Pact Broker** (в проекте есть `docker-compose` сервис `pact-broker`) и **бэкенд** с тестовыми настройками, если нужны provider states.
2. Consumer:

```bash
cd tests/pact/consumer
npm install
npm test
npm run publish:pacts   # при необходимости, с PACT_BROKER_BASE_URL
```

3. Provider verification:

```bash
set PROVIDER_URL=http://localhost:8000
set PACT_BROKER_BASE_URL=http://localhost:9292
python tests/pact/provider/pact_verifier.py
```

## 13. Линтер и статический анализ (актуальный стек для JavaScript / React)

В экосистеме фронтенда чаще всего используют связку **ESLint** + **Prettier**. Второй инструмент в паре обычно называют не «линтером», а **форматтером**; для «чистоты» на уровне типов в типизированных проектах к ним добавляют **TypeScript** (`tsc`). Ниже — кратко по каждому и зачем это QA.

### ESLint

- **Что делает:** проверяет JavaScript/JSX по настраиваемым правилам: потенциальные ошибки (`no-undef`, сравнения с `==`), стиль, доступность React, импорты, хуки (`eslint-plugin-react-hooks`), ограничения сложности.
- **Польза для QA:** дефекты и запахи кода всплывают **до** ручного и автоматического тестирования; единый стиль облегчает ревью и снижает риск регрессий из-за «мёртвого» кода или опасных конструкций.

### Prettier

- **Что делает:** автоматически форматирует код (отступы, кавычки, переносы) по одному стилю, без споров о вкусе.
- **Польза для QA:** стабильные диффы в CI, меньше шума при проверке изменений; удобно сочетать с ESLint (через `eslint-config-prettier`, чтобы правила не конфликтовали).

### TypeScript (опционально, если проект на `.ts` / `.tsx`)

- **Что делает:** статическая проверка типов (`tsc --noEmit` или сборка через `tsc`).
- **Польза для QA:** раннее обнаружение несоответствий контрактам данных между слоями UI и API.

### Как подключить к этому репозиторию (фронтенд)

Из каталога `frontend`:

```bash
cd frontend
npm install --save-dev eslint eslint-plugin-react eslint-plugin-react-hooks @eslint/js globals
```

Добавьте конфигурацию (пример для ESLint 9 flat config — `eslint.config.js`; для классического формата — `.eslintrc.cjs`). Подключите `eslint-plugin-react` и `eslint-plugin-react-hooks` для React 16.

Пример скрипта в `package.json`:

```json
"scripts": {
  "lint": "eslint src unit_test"
}
```

Запуск:

```bash
npm run lint
```

Prettier (по желанию):

```bash
npm install --save-dev prettier eslint-config-prettier
```

## 14. Покрытие кода (coverage) для юнит-тестов

### Фронтенд (JavaScript, Jest)

В проекте уже настроено:

- Конфиг: `frontend/unit_test/jest.config.cjs` — `collectCoverageFrom: ["src/**/*.js", ...]`, пороги `coverageThreshold` на **100%** по строкам/веткам/функциям/операторам.
- Скрипт в `frontend/package.json`: `test:unit:coverage` → запуск Jest с `--coverage`, отчёты в `frontend/coverage/unit` (HTML, lcov).

Запуск:

```bash
cd frontend
npm run test:unit:coverage
```

Отчёт HTML: `frontend/coverage/unit/index.html`. Для QA полезно смотреть **не только процент**, но и **непокрытые строки** в HTML-отчёте перед релизом.

**Как это устроено:** Jest использует встроенный сборщик покрытия (Istanbul). Дополнительные опции можно передать: `npx jest --config unit_test/jest.config.cjs --coverage --collectCoverageFrom='src/**/*.js'`.

### Бэкенд (Python, pytest-cov)

Юнит-тесты: каталог `backend/unit_test`. Покрытие пакета приложения задаётся через `pytest` и `coverage` (см. `backend/pyproject.toml` и `backend/setup.cfg`).

Пример:

```bash
cd backend
python -m pytest unit_test --cov=app --cov-report=html --cov-report=term
```

HTML-отчёт по умолчанию: `backend/htmlcov/index.html`. Порог **100%** по `app` может быть задан через настройки coverage/pytest в проекте.
