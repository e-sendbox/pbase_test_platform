# Паттерны

- **Repository pattern**: каждая сущность — отдельный репозиторий (`UsersRepository`, `ArticlesRepository`, …). Репозитории получают `asyncpg.Connection` через DI.
- **Settings по окружению**: `get_app_settings()` возвращает LRU-кэшированный инстанс одного из трёх классов настроек.
- **SQL-файлы через aiosql**: все запросы хранятся в `*.sql`-файлах, загружаются как Python-функции с сохранением имён.
- **Lifespan-хуки**: пул соединений создаётся при старте приложения и закрывается при остановке.

# Компоненты по отдельности

### Docker-сеть `conduit-network`

- Тип: **external** в `docker-compose.yml`, имя фиксировано: `conduit-network`.
- Нужна, чтобы контейнеры из `docker run` (Pact CLI) и job’ы раннера резолвили `pact-broker`, `db`, `gitea` так же, как сервисы Compose.
- Создание: автоматически в `01-start-infrastructure.sh` или вручную: `docker network create conduit-network`.

### PostgreSQL (`db`, контейнер `conduit-db`)

- Одна инстанция, несколько БД (см. `docker/db/init-databases.sql`): `conduit_db`, `gitea_db`, `pactbroker_db`, плюс для тестов используется `conduit_test_db` (создаётся скриптами/пайплайном при необходимости).
- Доступ с хоста: `localhost:${POSTGRES_PORT}` (по умолчанию 5432), пользователь `postgres`, пароль в compose не задан (`trust`).

### Pact Broker (`pact-broker`, `conduit-pact-broker`)

- URL с хоста: `http://localhost:${PACT_BROKER_PORT}` (по умолчанию 9292).
- Внутри сети: `http://pact-broker:9292`.
- Режим с ослабленными ограничениями на изменение контрактов включён для учебного стенда (`PACT_BROKER_ALLOW_DANGEROUS_CONTRACT_MODIFICATION`).

### Gitea (`gitea`, `conduit-gitea`)

- Порт HTTP на хосте: `${GITEA_PORT}` → контейнерный 3000.
- Конфигурация: `docker/gitea/app.ini` (в т.ч. БД и Actions). При типичной поставке **мастер установки в браузере не обязателен**, если данные Gitea уже инициализированы с этим конфигом.
- Организация и репозиторий для автоматизации: **`conduit/monorepo`** (создаётся `02-setup-gitea.sh`).

### act-runner (`act-runner`, `conduit-act-runner`)

- Кастомный образ `docker/runner/Dockerfile`: Node/npm для actions, **Docker CLI** и плагин **Compose v2** (сборка образа приложения в job «Build and Deploy»).
- Подключается к Gitea по `http://gitea:3000` (изнутри сети).
- **Тома:** Docker socket, данные раннера, **`./workspace:/workspace`** — сюда попадает checkout и отсюда же берётся контекст для шагов `run`.
- Метки раннера: `self-hosted`, `ubuntu-latest` и др. (см. `docker/runner/config.yaml`).
- Сеть job’ов задаётся в `config.yaml` (`container.network: conduit-network`), чтобы `docker run` с брокером был в той же сети.

### Приложение Conduit (`app`, `conduit-app`)

- Сборка: `docker/app/Dockerfile` (multi-stage: backend + frontend).
- С хоста: `http://localhost:${APP_PORT}` → порт 80 в контейнере (Nginx, прокси на API).
- Health: `GET /health`.
- Монтирует **`./workspace:/workspace`** и `./scripts` — пайплайн копирует в контейнер свежий код в `/workspace/conduit/monorepo`.

# Схема `conduit_db` (Alembic-ревизия `fdf8821871d7`)

```
users
  id (bigserial PK)
  username (unique, not null)
  email (unique, not null)
  salt (not null)
  hashed_password (not null)
  bio (nullable)
  image (nullable)
  created_at, updated_at (auto-triggers)

followers_to_followings
  follower_id  → users.id
  following_id → users.id
  PK(follower_id, following_id)

articles
  id (bigserial PK)
  slug (unique, not null)
  title, description, body (not null)
  author_id → users.id (SET NULL on delete)
  created_at, updated_at (auto-triggers)

tags
  tag (PK, varchar)

articles_to_tags
  article_id → articles.id
  tag        → tags.tag
  PK(article_id, tag)

favorites
  user_id    → users.id
  article_id → articles.id
  PK(user_id, article_id)

commentaries
  id (bigserial PK)
  body (not null)
  author_id  → users.id
  article_id → articles.id
  created_at, updated_at (auto-triggers)
```

Все `updated_at` обновляются автоматически через PL/pgSQL-триггер `update_updated_at_column`.

# Связь каталога репозитория и workspace раннера

**Это важно для понимания, откуда что пушится и где выполняется checkout:**

| Место                                             | Что это                                                                                                                                                                                                      |
| ------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Корень клона на вашей машине**                  | Ваша рабочая копия монорепозитория (тот же состав, что уходит в Git). Сюда вы вносите изменения и откуда запускаете `03-push-code.sh`.                                                                       |
| **Репозиторий в Gitea**                           | Удалённый `conduit/monorepo` — каноническая копия для CI.                                                                                                                                                    |
| **Каталог `workspace/` в корне проекта на хосте** | Общий bind-mount для `act-runner` и `app`. В него раннер кладёт результат **checkout** (например `workspace/conduit/monorepo`). Содержимое **не коммитится** (см. `.gitignore`).                             |
| **Файл пайплайна в Git**                          | В репозитории должен быть `.gitea/workflows/pipeline.yaml`. Скрипт `03-push-code.sh` **копирует** его из канона `docker/gitea/pipeline.yaml`, чтобы правки workflow делались в одном месте и затем пушились. |

Итого: **пуш идёт из корня вашего локального репозитория в Gitea**; **выполнение шагов workflow** идёт в окружении раннера с рабочим каталогом под `workspace/`, после чего код дополнительно синхронизируется в контейнер `conduit-app` для `docker exec` шагов.


1. **Основная рабочая копия** — каталог клона монорепозитория на вашей машине (корень проекта).
2. Удалённый репозиторий CI — **Gitea**: `conduit/monorepo`, ветка **`main`**.
3. Удобный способ залить всё впервые и обновить workflow: **`./scripts/03-push-code.sh`** (remote имя `gitea`).
4. Если вы клонировали уже **из Gitea**:
---
Источник правды для описания шагов в Git: **`docker/gitea/pipeline.yaml`** (копируется в `.gitea/workflows/` при push-скрипте).

Задачи (jobs):

1. **Frontend Pact Tests** (`frontend`) — checkout → синхронизация в `conduit-app` → установка зависимостей и запуск Jest Pact в `tests/pact/consumer` → публикация контрактов в брокер (`pactfoundation/pact-cli`).
2. **Backend Tests and Pact Verification** (`backend`, после `frontend`) — poetry, миграции, pytest, сброс данных для проверки, подъём API на порту 8001, `pact_verifier.py` против брокера.
3. **Pact Can-I-Deploy Check** (`deploygate`) — окружение `production` в брокере, запись деплоя провайдера, `can-i-deploy` для consumer, запись деплоя consumer при успехе.
4. **Build and Deploy** (`imagebuild`) — `docker compose build app` и `docker compose up -d --no-deps app` с **`COMPOSE_PROJECT_NAME`**, считанным с меток **уже запущенного** контейнера `conduit-app` (чтобы не создавать второй контейнер с тем же именем).
5. **Notify Status** (`notify`, `if: always()`) — сводка статусов jobs.

Все задачи с `runs-on: self-hosted` выполняются на **act-runner**; шаги с `docker exec` и `docker compose` используют Docker хоста через сокет.


**Логика потока данных в CI:**

1. Раннер делает **checkout** репозитория в каталог внутри примонтированного `workspace` (например `workspace/conduit/monorepo`).
2. Шаги пайплайна упаковывают файлы checkout в **`conduit-app:/workspace/conduit/monorepo`** (`tar` + `docker exec`), чтобы команды внутри контейнера приложения видели тот же код.
3. Публикация контрактов и `can-i-deploy` используют контейнер **`pactfoundation/pact-cli`** с сетью `conduit-network`.

# 14. Логи: где смотреть и что означают

Все сервисы работают внутри Docker-контейнеров. Основной инструмент просмотра — `docker logs <container>`.

### Сводная таблица логов

| Источник лога | Команда просмотра | Что содержит |
|--------------|------------------|-------------|
| FastAPI / Uvicorn | `docker logs conduit-app` | HTTP-запросы к `/api`, Python-исключения, Loguru-сообщения приложения |
| Nginx access | `docker logs conduit-app` | Все входящие HTTP-запросы (метод, путь, статус, размер, latency) |
| Nginx error | `docker logs conduit-app` | Ошибки проксирования, 4xx/5xx, проблемы с upstream |
| Supervisord | `docker exec conduit-app cat /var/log/supervisor/supervisord.log` | Старт/стоп процессов nginx и uvicorn, рестарты при падении |
| PostgreSQL | `docker logs conduit-db` | Подключения к БД, ошибки запросов, checkpoint-события |
| Pact Broker | `docker logs conduit-pact-broker` | Загрузка/верификация контрактов, HTTP-запросы брокера |
| Gitea | `docker logs conduit-gitea` | Git-операции, Actions-триггеры, ошибки аутентификации |
| Act-Runner | `docker logs conduit-act-runner` | Регистрация раннера, получение и выполнение CI-джобов |

### Детальное описание

#### `docker logs conduit-app`

Агрегирует вывод **двух процессов** (Nginx + Uvicorn), так как supervisord перенаправляет оба в `stdout`/`stderr` контейнера.

- **Nginx access**: каждая входящая строка HTTP-запроса. Нужен для: анализа трафика, отладки frontend-маршрутизации, проверки статус-кодов.
- **Nginx error**: проблемы с проксированием на `localhost:8000`. Нужен для: диагностики когда приложение вернуло ошибку или недоступно.
- **Uvicorn / FastAPI**: строки вида `INFO: 127.0.0.1:PORT - "POST /api/users/login HTTP/1.1" 200`. Loguru-сообщения содержат уровень (INFO/ERROR/DEBUG) и трассировку исключений. Нужен для: отладки бизнес-логики, JWT-ошибок, ошибок БД.

```bash
# Живой поток логов приложения
docker logs -f conduit-app

# Только последние 100 строк
docker logs --tail 100 conduit-app

# Фильтрация ошибок
docker logs conduit-app 2>&1 | grep -i error
```

#### `docker logs conduit-db`

PostgreSQL пишет события старта, подключений и критических ошибок.

- **Нужен для**: диагностики `ConnectionRefused` в приложении, проверки выполнения `init-databases.sql` при первом старте.

```bash
docker logs conduit-db
docker logs -f conduit-db  # live
```

#### `docker logs conduit-pact-broker`

Pact Broker логирует HTTP-запросы на публикацию и верификацию контрактов.

- **Нужен для**: отладки проблем при `pact publish` / `pact verify`, проверки что контракт принят брокером.

```bash
docker logs conduit-pact-broker
```

#### `docker logs conduit-gitea`

Gitea пишет события: push, создание PR, Actions-триггеры, ошибки webhook.

- **Нужен для**: диагностики когда пайплайн не запускается после push, ошибок конфигурации Actions.

```bash
docker logs conduit-gitea
docker logs -f conduit-gitea
```

#### `docker logs conduit-act-runner`

Act-runner пишет: регистрацию в Gitea, получение джобов, stdout/stderr каждого шага пайплайна.

- **Нужен для**: диагностики упавшего CI-шага, отслеживания прогресса выполнения пайплайна в реальном времени.

```bash
docker logs -f conduit-act-runner
```

> Вывод пайплайна также видно в **Gitea UI**: `http://localhost:3001` → репозиторий → Actions.

#### Supervisord внутри контейнера

```bash
docker exec conduit-app cat /var/log/supervisor/supervisord.log
```

- **Нужен для**: диагностики когда uvicorn или nginx упали и supervisord их перезапускает в цикле.
